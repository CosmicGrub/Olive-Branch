Build against the Olive Branch server

A small Node server in front of Postgres, where the database enforces the product's prohibitions and the API layer cannot forget to ask. This portal is generated from the source, so the numbers below are counted, not typed.

Getting started

Auth in five minutes

Every request carries a signed session token. There are two ways to get one: the real path, which is a device pairing, and a development shortcut that only exists when you start the server with DEV_LOGIN=1.

Development only

POST /v1/auth/dev-login mints a session for any user or child id with no credential. It answers 404 unless DEV_LOGIN=1, and the process refuses to start if DEV_LOGIN=1 and NODE_ENV=production are both set. Production compose pins DEV_LOGIN: "0".

Base URL and a first call #

The dev compose file publishes the server on loopback only: 127.0.0.1:8123. Devices reach it through adb reverse tcp:8123 tcp:8123.

curl -s http://127.0.0.1:8123/healthz # {"status":"ok"} (503 {"status":"db_unreachable"} after a 3 s timeout)

The prod compose file publishes 127.0.0.1:${SERVER_HOST_PORT:-8123} as well; TLS and a public hostname are yours to put in front. The WebAuthn relying party in routes.mjs is still the placeholder olivebranch.local and must become the deployed domain first (see Security).

curl -s https://api.example.invalid/healthz

The real path: pair, refresh, sign out #

A guardian on a device that is already signed in generates a short-lived code. The new device redeems it once and receives a one-hour session token plus a long-lived device credential, shown exactly once. The device then keeps itself signed in by refreshing with that credential. Signing out revokes the device on the server.

What the code guarantees
  • Refresh answers 401 invalid_device_credential identically for an unknown id, a wrong credential, another device's credential and a pre-0038 device, so it is not a device-id oracle.
  • The credential is 256 random bits. Only its SHA-256 is stored. It is not rotated on use, on purpose: rotation would strand a kiosk whose response was lost in transit.
  • A revoked device is refused on its very next request, because handle() checks paired_device for every session carrying a deviceId claim.

The development shortcut #

Start the dev stack with DEV_LOGIN=1 in scaffold/.env, seed it, then mint a token for a seeded id. The seed (server/seed-dev.mjs) creates Ivy (child), Dad and Mom (guardians).

curl -s -X POST http://127.0.0.1:8123/v1/auth/dev-login \ -H 'content-type: application/json' \ -d '{"userId":"aaaaaaaa-0000-4000-8000-000000000002"}' # {"token":"eyJ1c2VySWQiOi...<mac>"} (guardian: Dad) curl -s -X POST http://127.0.0.1:8123/v1/auth/dev-login \ -H 'content-type: application/json' \ -d '{"childId":"aaaaaaaa-0000-4000-8000-000000000001"}' # a child session for Ivy

Token inspector #

A session token is base64url(JSON payload) + "." + base64url(HMAC-SHA256). The payload is readable by anyone holding the token; the MAC is what makes it trustworthy. This decodes locally in your browser, verifies nothing, and sends nothing.

Concepts

How the server decides

Five locks sit between a request and a row. Each is enforced somewhere that does not depend on a route author remembering it.

Principals and roles #

A verified session produces one principal: {userId, roleName, childId, escalated, deviceId}. A child principal has userId: null and a childId. An adult principal has a userId and no childId; what they may do for a given child comes from their guardianship edges, re-read on every request, so a revoked edge takes effect immediately even though the token is stateless.

Generated from ROLE_CAPS in packages/family-graph/src/authorize.ts. The child column is not a role in that table: the API gate lets a child act only on her own childId, and denies expense.* (P6) and journal.read (P7) outright. letter is held by no adult role at all.

Actions and can() #

Each route declares an Action (or null for identity-only). register() throws if a route has no declared action, and also if a :childId route says null without the explicit identityScopedByHandler escape hatch. The childId is read from the path only, never from a body, query or header.

  1. P7 first, for everyone. journal.read returns P7_journal_never. No role, tier, escalation or court order changes that.
  2. P6 for children. A child actor asking for any expense.* action gets P6_child_financial.
  3. Edges for this child. No edge: no_edge. Then every edge is tried; the most specific denial wins.
  4. Per edge: closed, expired, outside its validity window, restricted, contact blocked by ladder step none, write blocked by observerOnly, role lacks the action, an explicit scope of false.
  5. Court tier. export.certified additionally requires the tier flag, else tier_required.

RLS and FORCE #

The API check is the second lock. The first is Postgres. Each request that touches data runs inside a transaction whose app.role, app.child_id and app.user_id settings are set from the verified principal and never from input. An unconfigured session sees zero rows, not all of them.

Why FORCE matters

A table's owner bypasses row-level security unless FORCE ROW LEVEL SECURITY is also set, and most applications connect as the owner. db/test/0001_constraints.test.sql measured it: with ENABLE only, the owner read 1 row of the journal; with ENABLE plus FORCE, 0. The application role must also be NOSUPERUSER NOBYPASSRLS, because superusers bypass RLS even with FORCE.

See Data model for the per-table status. The health_check view's rls_unforced row watches a hand-maintained list of tables; the generator confirmed that list matches the forced tables in the migrations today.

Child-payload sweep and banned keys #

Every response to a child principal passes through one choke point in handle(): a recursive walk that fails the request with 500 child_payload_leak (listing the offending paths) if any key, case-insensitively, is on GLOBAL_CHILD_FORBIDDEN. It fails closed. The one exception is a route flagged skipChildPayloadSweep; today that is only POST .../handover (take-and-go), a deliberately complete self-export.

Naming has consequences: GET /v1/me returns yearsOld, not age, because age is banned and the sweep would 500 the route.

Request ids #

Every response carries x-request-id. If you send one that matches ^[A-Za-z0-9._-]{8,64}$ it is reused; anything else is replaced with a fresh UUID. The access log is one JSON line per request with the route template (never the concrete URL, so no child id and no query string leaks into logs).

{"ts":"2026-11-08T14:02:11.402Z","level":"info","msg":"request","id":"4f1c2d7e-9b0a-4c55-8d0e-2a6f0c1b7e11","method":"GET","route":"/v1/children/:childId/now","status":200,"ms":12.4}

Errors #

The envelope today is deliberately minimal: {"error": "snake_case_code"}, plus a few routes that add a field (stale_version adds currentVersion; child_payload_leak adds fields). There is no human message and no request id in the body. Branch on the status and the code. Anything unexpected is 500 {"error":"internal"} with details only in the log.

Proposed

A versioned envelope {error, message, requestId, details?} so a client can show the id to a support person. Additive, so it can ship under /v1. Tracked as API-04 on the roadmap.

Rate limits and size caps #

Coverage gap, read from the code

Only /v1/auth/* (by IP and by identifier) and the two game-table routes are rate limited. POST /v1/device-pairing/redeem is not under /v1/auth/, so it falls outside the limiter; see finding SEC-01 on the roadmap. Limits are in process memory, so they are per replica.

Idempotency proposed #

Not built

No route accepts an idempotency key today (the generator found none). A retried POST .../messages, .../expenses or .../care-notes creates a second row. Some routes are naturally idempotent (calls/:id/end, inbox/:id/opened, sign-out, DELETE /v1/me/device-tokens). The offline-first client will retry, so this is the first thing to add.

POST /v1/children/:childId/care-notes Idempotency-Key: 0b9f6a52-3c1d-4f0e-9d51-6a2a2d6c1e77 # Same key + same body within 24 h -> the original 201, replayed, with Idempotent-Replayed: true # Same key + different body -> 422 idempotency_key_reused # In flight -> 409 idempotency_in_progress

Pagination proposed #

Not built

No list route takes limit or a cursor. The only query parameter on any built route is kind on GET .../export. Lists such as the inbox, expenses, care notes and handover notes return everything the caller may see.

GET /v1/children/:childId/handover-notes?limit=50&after=eyJzZXEiOjQyfQ # 200 {"items":[...], "next":"eyJzZXEiOjkyfQ"} (next is null on the last page) # Handover notes already have a gapless per-child "seq", which makes a stable cursor free.

If-Match built, one route #

The emergency card is the one resource with optimistic concurrency, added after an audit found it was last-write-wins between two guardians. It is a body field, not the HTTP header: PUT .../emergency-card requires an integer ifMatch equal to the version you read. Missing: 428 if_match_required. Stale: 409 stale_version with currentVersion. Each write appends the replaced values to the append-only medical_record_history.

{ "ifMatch": 3, "bloodType": "O+", "allergies": ["penicillin"], "conditions": [], "pediatricianName": "Dr. Rao", "pediatricianPhone": "+1 555 0100" } // 409 {"error":"stale_version","currentVersion":4} -> refetch, merge, resend with ifMatch: 4

Data model

The tables

The append-only message log and its hash chain #

message_log is the parents' channel and the backbone of the certified court export. Entries are never edited or deleted (P8). Each row stores the hash of the previous row, so a change anywhere breaks everything after it.

The database enforces

Primary key (child_id, seq). Hash columns match ^[0-9a-f]{64}$. A BEFORE INSERT trigger requires the first row to be seq 0 linked to genesis, and every later row to link to the current head with a contiguous seq. BEFORE UPDATE and BEFORE DELETE triggers raise, so a row can neither be changed nor removed.

Only the app recomputes

The trigger checks linkage, not that hash equals the hash of the row's content. That recomputation lives in packages/ledger and runs when a certified export is built (chain_broken refuses the export). A writer with insert rights could store a self-consistent but wrong hash. See finding DATA-02.

Monitored

The log_sequence_gap health check flags any non-contiguous sequence, and rls_unforced watches the table's FORCE flag.

Realtime

Game tables over WebSocket

Live checkers is the only realtime channel the server owns. It is an in-memory relay on the same HTTP server and port: no Postgres rows, no disk, no second listener. A dropped connection ends the game.

Scope

Calls run on LiveKit (the server only mints tokens, see POST .../calls). Co-viewing has no server transport yet. Tables hold at most checkers today.

Open, join, connect #

  1. POST /v1/game-tables with {game, partnerChildId | partnerUserId}. Authorized by canOpenTable: guardian to child uses the same can('call') gate as calls; sibling to sibling needs a sibling_link with contact allowed. Returns {tableId, seat, token, ttlSeconds, wsPath}. A child caller takes seat 0 and moves first.
  2. The partner calls POST /v1/game-tables/:tableId/join from their own session and gets their own seat token. Authorization is re-run for both sides.
  3. Each side opens wss://host/v1/game-tables/:tableId/socket?token=<token>. The token is verified before the upgrade completes; any failure destroys the socket at TCP level with no HTTP response. A token is single-use: replaying it, or a third party presenting a copy while the real device is connected, is refused.
const { tableId, token, wsPath } = await post('/v1/game-tables', { game: 'checkers', partnerUserId }); const ws = new WebSocket(`wss://api.example.invalid${wsPath}?token=${encodeURIComponent(token)}`); ws.onmessage = (e) => { const m = JSON.parse(e.data); if (m.type === 'welcome') { /* { seat, status, turnSeat } */ } if (m.type === 'peer_joined') { /* both seats are connected; status is now 'active' */ } if (m.type === 'move') { /* the other seat's move: { seat, from, to, continues } */ } if (m.type === 'table_closed') { /* { reason } - the table is gone for good */ } }; ws.send(JSON.stringify({ type: 'move', from: [5, 0], to: [4, 1], continues: false }));

Limits and close codes #

Single replica

Tables, tokens' bookkeeping and the HTTP rate buckets live in one process's memory. Two replicas could not see each other's tables. The signing key is derived from SESSION_SECRET by HMAC with the label olive-branch:game-table-v1, which is key separation, not new cryptography.

Jobs and scheduler

What runs when

There is no cron and no queue. One process, tools/scheduler.mjs loop, wakes once a day and runs five jobs in order. A few timers live inside the server itself.

The scheduler #

Default schedule: once daily at SCHEDULER_HOUR_UTC (default 3), or every SCHEDULER_INTERVAL_MS if set. In production compose it is on by default; in dev it sits behind --profile scheduler so it cannot rewrite rows under a developer mid-debug. node tools/scheduler.mjs run <job|all> runs one job by hand.

Not wired

Health checks #

The health_check view has eight rows; any breach makes npm run health exit non-zero and health-alert print an ALERT check_name=... line. It adds backup_stale when BACKUP_DIR is set. There is no pager or email integration.

Passkeys #

  • Guardians sign in with WebAuthn, ES256. The challenge is stored per user, single-use and valid 5 minutes; it is consumed before the signature is checked, so a failed attempt still spends it.
  • The sign counter is advanced with a compare-and-swap. Losing the race returns 401 signcount_replay, which is what a cloned authenticator used at the same moment produces.
  • A deactivated account is refused at login even with an older credential (403 account_deactivated).
  • The relying party id is the placeholder olivebranch.local and the origin https://olivebranch.local. Until they become the deployed domain, no real ceremony can pass its own origin check.

PIN #

A guardian PIN gates the kiosk lock, pairing-code creation and the parental-controls screen. It is hashed with scrypt (N=32768, r=8, p=1) with a per-PIN salt, because a 4 to 8 digit secret has a tiny keyspace and the only defence against an offline attack is making each guess expensive. After 5 wrong attempts the credential locks for 15 minutes, in the database, so it survives a restart. Changing a PIN that exists requires the current one through the same lockout path (current_pin_required).

Device credentials #

A paired device is a row in paired_device with a credential_hash (migration 0038). Identity always comes from that row, never from the refresh body. A device paired before 0038 has a NULL hash, never matches anything, and must re-pair when its last session lapses.

Machinery that exists but is not connected #

Escalation

escalateSession() (PIN and biometric, 15 minute session) and the escalated route flag in api.ts exist and are unit tested, but no route sets escalated: true and nothing outside tests calls escalateSession(). POST .../kiosk-pin/verify returns only {ok: boolean}. Treat escalation as designed, not shipped. Finding SEC-02.

A release cut gathering eleven [Unreleased] entries (PRs #119 to #147) and bringing MASTERFILE, MARKUP and DEMO to parity with the code. Versioning policy proposed #

Today every path starts with /v1, but that prefix is a convention, not a policy. The CHANGELOG applies Semantic Versioning to the specification, not to shipped software, and the server sends no version header. A proposal that keeps both honest:

New route, new optional request field, new response fieldYesChangelog; clients must ignore unknown fields
New error code on an existing statusYesChangelog; clients must treat unknown codes by status class
New value in an enum the client sendsYesChangelog
Remove or rename a field, tighten validation, change a statusNo: needs /v2 of that routeDeprecation, Sunset and Link: rel="successor-version" on the old route for at least one release train
Remove a routeNoSame headers, then 410 gone after the sunset date
